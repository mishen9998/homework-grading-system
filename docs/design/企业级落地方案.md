# 作业系统落地与企业级演进方案

## 当前交付与边界

本轮完成上线基础加固，并提供独立 compose.production.yml，保持本机开发方式可用。
当前定位是单机构试点系统，不能作为已经完成多租户隔离的 SaaS 销售。
尚未部署公网：需要目标 Linux 服务器、域名和 DNS、HTTPS 入口；本机 Docker 引擎尚未运行。

已实施：禁止公开注册管理员；生产环境关闭公开注册；管理员接口读取数据库中的实时角色；生产密钥强度检查；生产环境禁止启动时隐式建表；空库初始化和交互式管理员创建；数据库就绪检查；构建排除密钥、数据库和附件；前端确定性安装；修复附件 URL 被静态缓存规则截获；MySQL 专用应用账号、持久卷、内部端口、健康检查与启动依赖。

## 快速部署：先做受控试点

建议保留 Vue + Flask 模块化单体，以减少运维负担。部署拓扑：HTTPS 网关 → Nginx/Vue → Gunicorn/Flask → MySQL。AI 仍由后端调用。先对一个机构和少量教师开放，根据实测负载扩容；不要把机器配置当作并发承诺。

准备 Linux 主机及 Docker Engine/Compose，上传源码（排除 .env、venv、node_modules、数据文件、instance 和上传目录）。本地53个测试账号不导入生产。

1. 复制 deploy.env.example 为 deploy.env。为四个密钥分别生成独立的64位十六进制随机值，填写域名与 AI 密钥。部署文件权限设为仅管理员可读。MYSQL_PASSWORD 使用十六进制避免连接串转义问题。
2. 在项目根目录执行（首次空库）：

```sh
docker compose --env-file deploy.env -f compose.production.yml build
docker compose --env-file deploy.env -f compose.production.yml up -d mysql
docker compose --env-file deploy.env -f compose.production.yml run --rm backend python initialize_database.py
docker compose --env-file deploy.env -f compose.production.yml run --rm backend python create_admin.py
docker compose --env-file deploy.env -f compose.production.yml up -d
docker compose --env-file deploy.env -f compose.production.yml ps
curl --fail http://127.0.0.1:8080/api/status/ready
```

3. 在宿主机 HTTPS 网关配置域名证书，反向代理到 127.0.0.1:8080，AI请求超时至少210秒。只对外开放HTTPS及必要的管理入口。现有部署配置仅绑定本机8080，不直接公开HTTP。
4. 使用管理员导入教师、学生；验收登录、课程归属、发布作业、提交、批改、查看成绩、中文附件、AI异常提示。

initialize_database.py 只允许空库，更新已有库不能重复执行。现有 Alembic 初始版本实际只修改两张表，不能当作空库建表脚本；本轮未伪造完整迁移历史。后续升级前应以实际结构建立并核验迁移基线。

## 公网开放前的验收门槛（尚需实施）

- 全量对象权限：每个课程、作业、题目、提交、资源请求都校验所属机构、教师或选课关系；学生接口禁止输出参考答案。使用跨教师、跨学生反例验证。现有部分查询只有登录检查，不能仅靠页面隐藏。
- 附件授权：现有 /tupian 文件按URL公开读取，学生作业等敏感附件应迁移到鉴权下载或短期签名链接；验证文件实际类型，限制大小并隔离存储。
- 登录限流、密码重置、首次登录改密、管理员MFA或组织SSO。开发账号的统一密码不能用于真实客户。
- AI结果先进入建议草稿，经老师确认后发布；现有单题AI评分会直接写入答案记录，需统一改成草稿状态。学生文本与模型输出均视为不可信输入。
- 依赖漏洞扫描及升级回归、容器非root运行、日志脱敏、HTTPS配置检查和备份恢复演练。

## 企业级演进顺序

阶段一（约1–2周，依人员与验收调整）：完成上述权限和附件整改；补充核心业务回归、登录限流、操作审计；单机构封闭试点。验收：越权用例全部拒绝，成绩只有确认后可见，备份能恢复。

阶段二（约2–4周）：引入 Redis + Celery/RQ 执行批量批改，任务状态、重试上限、取消、幂等键、进度反馈；数据库事务保证作业和题目一起发布。支持老师复核队列、评分依据、模型/提示词版本、调用成本与配额。验收：重复点击不重复扣费或发布，进程重启任务可恢复，失败可追踪。

阶段三（约4–8周）：机构/校区/班级多租户模型与所有查询隔离；RBAC、SSO、机构配额、数据导出删除及留存策略；对象存储、审计导出、监控报警、灰度发布。验收：跨租户渗透回归、容量压测、真实备份恢复演练；涉及学生信息和第三方AI的数据处理流程由机构确认。

交付原则：先服务一个真实班级，跟踪教师每份作业耗时、AI建议采纳率、人工改分率、失败率及成本；未验证教学质量前不承诺全自动评分。

## 运维、备份与回滚

上线前备份数据库及 pictures/uploads 卷；数据库可在 MySQL 容器内使用 mysqldump --single-transaction --routines --triggers，以环境变量提供密码，输出到受限备份目录。生产备份应加密复制到异地，设置保留期，并在独立数据库实际恢复验证；仅有导出文件不算完成演练。建议初期每日全量备份，明确最多丢失24小时数据；更严格要求需开启binlog并验证时间点恢复。

更新时保留上一版本镜像和数据库备份；先在预发布环境演练，再执行向前兼容迁移。仅回滚镜像无法撤回破坏性数据库变更。不要执行 docker compose down -v（会删除持久卷）。监控数据库就绪检查、5xx、磁盘空间、连接数、AI超时与成本；具体SLA以压测和试点数据制定。

本轮未修改本机MySQL root密码，也未删除开发数据；生产配置使用新的应用账号和独立数据库卷。
